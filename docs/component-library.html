MAW Foundation — Developer Guide

A reference for every package in the monorepo and every component in the ui-web design system — what it does, when to use it, and a working code sample.

Two-mode module architecture

MAW Foundation splits everything into two kinds of module. Knowing which kind you're touching tells you whether you're allowed to edit it.

MAW FOUNDATION │ ┌──────────────┴───────────────┐ │ │ FOUNDATION PACKAGES PROJECT MODULES │ │ @mawsoftwares/auth-core users @mawsoftwares/rbac-core customers @mawsoftwares/database orders @mawsoftwares/communication invoices @mawsoftwares/queue inventory @mawsoftwares/audit production │ │ └──────────────├───────────────┮ │ APPLICATION
KindLocationOwnerEditable?
Foundation Packagepackages/ (@mawsoftwares/*)FoundationNo — use the public API
Source ModuleCopied from templates/ into the projectProject developerYes — fully owned

Layered architecture

Foundation packages follow a strict layer hierarchy where dependencies flow downward only — nothing in a lower layer may import from a higher one. This is enforced by ESLint (pnpm lint) via .engineering/dependency-law.md.

┌────────────────────────────────────────────│ │ APPS │ │ sample-server │ sample-web │ (project apps) │ ├──────────────────────────────────────────│ │ PROJECT SOURCE MODULES │ │ modules/users │ modules/orders │ modules/... │ │ (copied from templates/, project-owned code) │ ├─────────────────────────────────────────│ │ SERVER ADAPTERS │ │ @mawsoftwares/server-express │ server-hono │ ├─────────────────────────────────────────│ │ DOMAIN PACKAGES │ │ @mawsoftwares/auth-core │ rbac-core │ tenancy │ │ communication │ queue │ audit │ feature-flags │ ├─────────────────────────────────────────│ │ PLATFORM PACKAGES │ │ @mawsoftwares/platform │ database │ observability │ ├─────────────────────────────────────────│ │ SDK / KERNEL │ │ @mawsoftwares/sdk │ core │ config │ └─────────────────────────────────────────┮

Key principles

Contracts over implementationsLogic depends on ports (interfaces), never on concrete engines, frameworks, or databases.
Framework-agnostic coreNo package below apps/ may import Express, Hono, Next, Expo, React DOM, or React Native (except ui-web and ui-native themselves).
Single authorization resolverresolveEffectiveAccess() in @mawsoftwares/rbac-core is the only can() used anywhere in the stack.
Multi-tenant by defaultEvery access decision is scoped by tenantId.
No anyNo hardcoded secrets; URLs/keys come from env, strings from i18n, colors from theme tokens.
Foundation vs. projectFoundation packages provide capabilities; project source modules implement domain behaviour.

When does something become a Foundation package?

Make it a Foundation package when…

  • Generic, reusable identically across multiple projects
  • Stable API — the interface rarely changes
  • No project-specific database fields or business rules
  • Represents infrastructure (auth, queues, files, notifications, audit)

Keep it a source module (copy from template) when…

  • Database fields or relationships change per project
  • Business rules, validation, or workflow differ between projects
  • API contract or UI requirements differ between projects
  • Represents domain/business logic

Full classification guide: docs/module-architecture.md.

Getting Started

Everything you need to get the monorepo running and understand the workflow.

Prerequisites

  • Node.js ≥ 20
  • pnpm (install via corepack enable or npm install -g pnpm)

Install & verify

# Clone the repository (foundation developers only)
git clone https://github.com/mawsoftwares/maw-foundation.git
cd maw-foundation

# Install all dependencies
pnpm install

# Run all verification checks
pnpm verify

Commands

CommandDescription
pnpm installInstall all workspace dependencies
pnpm typecheckRun TypeScript type checking
pnpm lintRun ESLint with dependency-law enforcement
pnpm testRun all tests with Vitest
pnpm buildBuild all packages
pnpm verifytypecheck + lint + test, in one shot
pnpm formatFormat all files with Prettier
pnpm sample:serverStart the Express proof backend
pnpm sample:webStart the Vite React proof app

Creating a new package

  1. Create packages/<name>/{package.json, tsconfig.json, src/index.ts, tests/, README.md}
  2. Set "name": "@mawsoftwares/<name>" in package.json
  3. Add the exports field: { "exports": { ".": "./src/index.ts" } }
  4. Add a path mapping in tsconfig.base.json
  5. Add an alias in vitest.config.ts
  6. Add dependency rules in eslint.config.js (which layer can it be imported from?)
  7. Add it to the root tsconfig.json include list

Testing

Tests use Vitest and live co-located with source files or in tests/ directories.

# Run all tests
pnpm test

# Watch mode
pnpm vitest

# A single package
pnpm vitest packages/config

Dependency rules

Enforced by ESLint — see .engineering/dependency-law.md. Each tier may only import tiers below it; violations fail pnpm lint.

sdk (imports nothing of ours) ↑ core / config ↑ platform / tenancy / modules / feature-flags ↑ rbac-core / auth-core ↑ server-express / server-hono (framework-specific) ↑ apps (composition roots)

Foundations

ui-web is a dependency-free, inline-style design system — no Tailwind, no Radix, no shadcn. Every component styles itself with plain style={{}} objects driven entirely by CSS custom-property tokens from @mawsoftwares/theme. Never hardcode a color, spacing value, or radius — always reference a var(--maw-*) token.

Per-tenant white-labeling

Call createTheme(tenantOverrides) from @mawsoftwares/theme to produce a merged token set — no component code changes needed for a new brand, just config.

import { createTheme, applyThemeVars } from '@mawsoftwares/theme';

const theme = createTheme({ brand: '#e11d48', brandLight: '#fb7185' });
applyThemeVars(document.documentElement, theme); // sets the --maw-* CSS vars

Dark mode

A dark palette (paletteDark) ships alongside the light one with the same token names — swap the applied token set based on prefers-color-scheme or a user setting; no component needs to know which mode is active.

@mawsoftwares/api-client

The typed HTTP client every frontend talks to the backend through. Axios-based under the hood, with retry/backoff, proactive JWT refresh, structured logging, request cancellation, and offline queueing built in.

Setting it up

import { ApiClient, webSecureStore } from '@mawsoftwares/api-client';

export const apiClient = new ApiClient({

Retry, offline, and logging

Retry/backoffOpt-in via the retry option (client-wide) or per-call via ApiRequestInit.retry. Only retries network errors, timeouts, and 5xx - never 4xx. Uses exponential backoff with full jitter (computeBackoffMs).
Offline queueOfflineRepository + installOfflineInterceptor queue mutations made while offline and replay them via SyncEngine when connectivity returns. isConnectivityFailure(err) distinguishes a real network failure from a genuine 4xx/5xx so errors aren't silently swallowed as "offline".
Logginglogging: true uses a built-in console logger; pass your own (entry: RequestLogEntry) => void to route into your observability pipeline instead.

Auth & Permissions

auth-core handles authentication (who are you); rbac-core handles authorization (what can you do). Both are framework-agnostic - server-express/server-hono are the adapters that wire them into an HTTP framework.

auth-core

import { hashPassword, verifyPassword, signAccessToken, verifyAccessToken, RefreshTokens } from '@mawsoftwares/auth-core';

// Registration
const passwordHash = await hashPassword(plainPassword);

// Login
const ok = await verifyPassword(plainPassword, user.passwordHash);
const accessToken = signAccessToken({ sub: user.id, tenantId: user.tenantId, role: user.role }, { secret });

// Verifying an incoming request

// Refresh token rotation
const refreshTokens = new RefreshTokens(refreshTokenStore);
const rotated = await refreshTokens.rotate(oldRefreshToken);

auth-core also ships MFA/OTP, login-attempt throttling (LoginProtection), email verification, password reset, and Google/GitHub social-auth providers - see the Package Reference above for the full export list.

rbac-core

resolveEffectiveAccess() is the single authorization resolver used everywhere in the stack - never hand-roll a permission check.

import { resolveEffectiveAccess } from '@mawsoftwares/rbac-core';

const access = resolveEffectiveAccess(
  {
    baseRole: user.role,
    grantedCapabilities: user.capabilities,
    enabledModules: tenant.enabledModules,
    rolePermissions: tenant.rolePermissionOverrides, // optional, falls back to config default
  },
  rbacConfig, // capabilities, defaultRolePolicy, isModuleEnabled - defined once per app
);

if (!access.permissions.has('orders.delete')) {
  throw new ForbiddenError();
}
